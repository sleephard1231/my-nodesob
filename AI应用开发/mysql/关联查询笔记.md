# 关联查询笔记：内连接、外连接与自连接（inner / left / right / self join）

> 对应《尚硅谷大模型技术之 MySQL2.0》"关联查询"章节
> 配套数据：`atguigu` 库的 `t_employee`（员工表）、`t_department`（部门表）、`t_job`（职位表）
> 练习前先执行：`use atguigu;`

---

## 一、为什么要关联查询？

数据**不是存一张表里的**，而是"员工放员工表、部门放部门表"，通过**关联字段**串起来：

- 员工表知道自己的 `did=1`，但"1 是什么部门？"得去部门表查
- 所以问"张三的部门叫什么" → 必须**两张表一起查** → 关联查询

**关联字段**：逻辑意义一样、数据类型一样的两个字段（这里就是两张表的 `did`）。可以建外键，也可以不建——**关联查询不要求必须有外键**。

---

## 二、关联查询语法总览

```
A inner join B on 关联条件      -- 内连接：取交集
A left  join B on 关联条件      -- 左连接：左表全保留
A right join B on 关联条件      -- 右连接：右表全保留
A join B on 条件1 join C on 条件2   -- 多表连接，每个 join 必须紧跟自己的 on
```

自连接也是上面这套语法，只是 **A 和 B 是同一张表**（详见第七节）：

```
t_employee as emp inner join t_employee as mgr on emp.mid = mgr.eid
```

---

## 三、关键背景：记住这 4 个事实

理解连接结果全靠它们：

1. 员工**李红、周洲**的 `did` 是 NULL（没部门）
2. 部门**3号测试部**没有任何员工
3. 员工表有 `did`，部门表也有 `did` → 这就是**关联字段**
4. 两张表靠 `did` 找到"这个员工属于哪个部门"

## 四、内连接（inner join）

### 4.1 语法

```sql
select ename, dname
from t_employee
inner join t_department
on t_employee.did = t_department.did;
```

**结果：13 行**（不是 15！）

### 4.2 语义：A∩B（交集）—— 核心

内连接 = **"两个表都有的部分"**：

| 情况 | 会出现吗 | 为什么 |
|------|---------|--------|
| 李红、周洲（did=NULL） | ❌ | 员工没有部门，匹配不上 |
| 3号测试部（没员工） | ❌ | 部门没员工，匹配不上 |
| 有部门的 13 个员工 | ✅ | 员工.did = 部门.did 能对上 |

> **内连接 = A ∩ B**（取交集）。写 SQL 前先想清楚"我要交集、还是全包含"。

### 4.3 为什么"这样写"？—— 逐行翻译成人话

| 代码 | 人话 |
|------|------|
| `select ename, dname` | 我要的结果：员工姓名 + 部门名称 |
| `from t_employee` | 姓名在员工表里（第一个表 = 主表） |
| `inner join t_department` | 光有姓名不够，拉上部门表一起 |
| `on t_employee.did = t_department.did` | **对齐规则**：两边 did 相等时，两行拼成一行 |

### 4.4 为什么两个表都有 did？

**did 是两张表之间的"接头暗号"**，故意这么设计：

- 员工表存 `did=1` → "我是 1 号部门的员工"
- 部门表存 `did=1, dname='研发部'` → "1 号部门叫研发部"

员工表**没必要**重复存"研发部"三个字（浪费空间，部门改名还要改一堆行），只存编号 `did`，要用部门名时**按编号去部门表查** → 这就是数据库的**消除冗余**思想，也是**外键**概念的由来。

### 4.5 为什么员工的 did 能和部门的 did 对上？

因为**它俩本来就是同一套编号**（全公司统一编的部门编号）：

```
t_employee 表：                t_department 表：
张伟   did = 1  ────────→   did = 1   研发部
杨洋   did = 1  ────────→
王芳   did = 2  ────────→   did = 2   市场部
```

`on t_employee.did = t_department.did` 就是**拿着员工表每行的 did，去部门表找 did 相等的那行，找到了就拼成一行**。

**"对上"的三个条件**（背下来）：
1. **逻辑意义一样**：都是"部门编号"
2. **数据类型一样**：都是 int
3. **名字可以一样也可以不一样**（这里恰好都叫 did）

### 4.6 坑 1：字段撞车（必须写"表名.字段"）

```sql
select ename, did, dname        -- ❌ 报错：did 两张表都有
from t_employee inner join t_department
on t_employee.did = t_department.did;

select ename, t_department.did, dname   -- ✅ 明确写哪张表的 did
from t_employee inner join t_department
on t_employee.did = t_department.did;
```

### 4.7 坑 2：不写 on → 笛卡尔积

```sql
select ename, t_department.did, dname
from t_employee inner join t_department;   -- ❌ 60 行（15×4）！
```

每个员工和每个部门都"配对"了一遍 → **笛卡尔积**（A 行数 × B 行数），全是错数据。

> **铁律：n 张表关联，写 n-1 个关联条件。** 2 张表 1 个，3 张表 2 个……少写一个数据就爆炸。

### 4.8 内连接 + where 筛选

```sql
-- 部门编号为 1 的女员工
select ename, gender, t_department.did, dname, salary
from t_employee inner join t_department
on t_employee.did = t_department.did
where t_department.did = 1 and gender = '女';
```

> 关联条件在 `on`，筛选条件在 `where`，两条别混。
> 补充：关联条件**也可以写进 `where`**（`from A inner join B where A.did = B.did`），但**强烈建议用 `on` 单独编写**——可读性更好，而且左/右连接中 on 和 where 的行为不一样（on 决定"怎么配"，where 决定"配完后再筛谁"，放错位置结果不同）。

### 4.9 三表连接

```sql
-- 每个 join 后面必须紧跟自己的 on
select ename, gender, t_department.did, dname, salary, job_id, jname
from t_employee
inner join t_department on t_employee.did = t_department.did
inner join t_job       on t_employee.job_id = t_job.jid
where t_department.did = 1;
```

## 五、左连接（left join）

### 5.1 语法 & 现象

```sql
select ename, dname
from t_employee
left join t_department
on t_employee.did = t_department.did;
```

**结果：15 行**（内连接只有 13 行），多出来的是李红、周洲，dname 是 NULL。

### 5.2 语义

> **左连接 = 左表（from 后面那张）全保留，右表能配上就配上，配不上的填 NULL。**

| 员工 | did | 内连接 | 左连接 |
|------|-----|--------|--------|
| 张伟 | 1 | ✅ 有部门 | ✅ 研发部 |
| 李红 | NULL | ❌ 被丢掉 | ✅ 保留，dname=NULL |
| 周洲 | NULL | ❌ 被丢掉 | ✅ 保留，dname=NULL |

> 集合记忆：**左连接 = A（全集）**，包括 A∩B 和 A 独有的部分。
> 人话：**以员工表为准，一个员工都不能少**，有部门的填部门名，没部门的空着。

### 5.3 和 inner 只差一个单词

```sql
from t_employee inner join t_department on ...;   -- 交集
from t_employee left  join t_department on ...;   -- 左表全留
```

## 六、右连接（right join）

### 6.1 语法 & 现象

```sql
select ename, dname
from t_employee
right join t_department
on t_employee.did = t_department.did;
```

**结果：14 行**，多出来的是**3号测试部**（ename 是 NULL）。

### 6.2 语义

> **右连接 = 右表（join 后面那张）全保留**，左表能配上就配上，配不上的填 NULL。

因为右连接 = **部门表全保留**（4 个部门，每个部门至少 1 行），测试部"一个员工都没有"也必须出现，ename 没得填 → NULL。

**行数怎么算的**：研发部 5 人 + 市场部 5 人 + 测试部 1 行（无员工）+ 运维部 3 人 = **14 行**。

### 6.3 left 和 right 可以互换

```sql
-- 这两句结果一模一样！
from t_employee left join t_department on ...;
from t_department right join t_employee on ...;
```

> **规律：`A left join B` = `B right join A`。** 实际工作中大家几乎只用 left join（右连接可以用调换表位置代替）。

## 七、自连接（self join）

### 7.1 自连接是什么？—— 物理一张表，逻辑两张表

**一句话：一张表自己跟自己 join。**

不是复制了一张表，而是**给同一张表起两个别名，把它当成两张表用**。这是自连接和普通连接最大的不同：**A 和 B 是同一张物理表**。

**为什么会需要它？** 因为有些"两类人/两类东西"其实**存在同一张表里**，比如：

- 员工 ↔ 领导：领导也是员工，都在 `t_employee` 表
- 菜单 ↔ 父菜单：父菜单也是菜单，都在菜单表
- 商品分类 ↔ 父分类：都在分类表

### 7.2 看数据：mid 字段的"双重身份"

```sql
select eid, ename, mid from t_employee;
```

`mid` 这一列存的是**"这个员工的领导是谁"**，值是领导的 `eid`：

| eid | ename | mid | 说明 |
|-----|-------|-----|------|
| 1 | 张伟 | NULL | 老板，没有领导 |
| 2 | 李红 | 1 | 领导是张伟（eid=1） |
| 4 | 王芳 | 1 | 领导是张伟 |
| 6 | 陈静 | 4 | 领导是王芳 |
| ... | ... | ... | ... |

**关键认知**：领导**也是员工**，他也在这张表里（张伟既是老板，也是李红的领导）。所以"员工"和"领导"两类角色，都在 `t_employee` 这一张表里 → 必须靠自连接"一张表当两张用"。

> 注意：**`mid` 的取值范围受 `eid` 限制**——mid 必须是某个员工的 eid（领导得先是个员工）。比如"李红的领导是张伟"，张伟的 eid=1 必须存在。

### 7.3 语法 & 现象

```sql
select
    emp.eid, emp.ename, emp.salary,   -- 员工自己的信息
    mgr.eid, mgr.ename, mgr.salary    -- 他领导的信息
from t_employee as emp
inner join t_employee as mgr
on emp.mid = mgr.eid;
```

**结果：14 行**（节选）：

| emp.eid | emp.ename | emp.salary | mgr.eid | mgr.ename | mgr.salary |
|---------|-----------|-----------|---------|-----------|------------|
| 2 | 李红 | 8000 | 1 | 张伟 | 25000 |
| 3 | 周洲 | 9000 | 1 | 张伟 | 25000 |
| 4 | 王芳 | 18000 | 1 | 张伟 | 25000 |
| 6 | 陈静 | 12000 | 4 | 王芳 | 18000 |
| ... | ... | ... | ... | ... | ... |

**每个员工一行，右边跟着他领导的信息**——"李红的领导是张伟，张伟月薪 25000"。

### 7.4 逐行拆解

```sql
from t_employee as emp    -- 视角 1：把它当成"员工表"
inner join t_employee as mgr   -- 视角 2：把它当成"领导表"（存领导信息的表）
on emp.mid = mgr.eid;      -- 员工表的"领导编号" = 领导表的"员工编号"
```

关键在于 `mid` 的"双重身份"：

```
对 emp（员工）来说：mid = 我领导的编号
对 mgr（领导）来说：eid = 我自己的员工编号
```

`on emp.mid = mgr.eid` 翻译成人话：

> **"每个员工的 mid（领导是谁），去 mgr 这张表里找 eid 相等的那个员工——那个人就是这个员工的领导。"**

### 7.5 和普通连接对比：完全一样的套路！

**普通连接**（员工表 join 部门表）：

```sql
from t_employee as e inner join t_department as d
on e.did = d.did;      -- 用 did 配对
```

**自连接**（员工表 join 员工表）：

```sql
from t_employee as emp inner join t_employee as mgr
on emp.mid = mgr.eid;  -- 用 mid 和 eid 配对
```

**一模一样！** 都是"拿 A 表的关联字段，去 B 表找相等的字段"。区别只是：普通连接的两张表是**不同的表**，自连接的两张表**物理上是同一张表**（靠别名分成两个逻辑表）。

### 7.6 关键细节（最容易懵的地方）

1. **`mid` 取值范围受 `eid` 限制**：mid 必须是某个员工的 eid（领导得先是个员工）eid是建表是的那个行号,是唯一的
2. **为什么结果不是 15 行？** 张伟的 mid 是 NULL（老板没领导），`inner join` 配不上 → 被丢弃。结果 **14 行**（15 人 - 老板张伟）
3. **表别名不是可选的**：自连接**必须**起别名（`emp`、`mgr`），否则 `t_employee.eid` 到底是哪个视角？MySQL 会懵。文档原话："把 t_employee 当成两张表，通过取别名的方式"
4. **老板就查不到了**：`inner join` 里老板（mid=NULL）不出现。想让"所有员工包括老板"都显示 → 用左连接
5. **自连接也能叠加 where**：比如"领导薪资比员工高"——在 `on` 后面继续加 `where mgr.salary > emp.salary`

### 7.7 自连接 + 左连接（老板也要显示）

```sql
select emp.ename as 员工, emp.salary as 员工薪资, mgr.ename as 领导
from t_employee as emp
left join t_employee as mgr
on emp.mid = mgr.eid;
-- 15 行，张伟的领导是 NULL
```

### 7.8 应用场景

自连接专门处理**同一张表内的层级关系**：
- 员工 ↔ 领导（本课例子）
- 菜单 ↔ 父菜单（多级菜单）
- 分类 ↔ 父分类（商品分类树）
- 地区 ↔ 上级地区（省市区）

> 特征：表里有个字段"指向本表的另一个 id"（mid 指向 eid）→ 99% 是自连接。

## 八、应用：查"没配上"的部分（经典题）

左/右连接 + `where ... is null`，把"没配上右表的那部分"单独拎出来：

```sql
-- 查"没有部门"的员工（A - A∩B）
select ename, salary, dname
from t_employee
left join t_department
on t_employee.did = t_department.did
where t_employee.did is null;    -- 结果：李红、周洲

-- 查"没有员工"的部门
select dname
from t_department
left join t_employee
on t_department.did = t_employee.did
where t_employee.did is null;    -- 结果：测试部
```

> ⚠️ 面试常考："查询没有 xxx 的员工/学生" 就是这个套路。
> ⚠️ `where` 里建议写**子表的关联字段 is null**（更准确），不要写 `dname is null` 这种。

## 九、三表连接 + 左连接（组合拳）

**查所有员工的姓名、部门名称、职位名称——注意是"所有员工"，没部门的也要有：**

```sql
select ename, dname, jname
from t_employee
left join t_department on t_employee.did = t_department.did
left join t_job       on t_employee.job_id = t_job.jid;
```

结果 15 行：李红、周洲 dname 是 NULL，但 jname 正常（职位有配上）。

## 十、四种连接一张表记完

| 连接 | 结果 | 用数据举例 | 行数 |
|------|------|-----------|------|
| `inner join` | A∩B（只留对得上的） | 有部门的员工 | 13 |
| `left join` | A（左表全留） | 含没部门的李红、周洲 | 15 |
| `right join` | B（右表全留） | 含没员工的测试部 | 14 |
| 自连接 `inner join` | 同一张表内配对的记录 | 员工和他的领导 | 14 |

> 自连接不是第四种连接类型，而是**同一张表上的 inner/left/right join**（把表起两个别名当两张表）。它是"连接类型"和"连接对象"两个维度的组合。

**判断口诀**：写 SQL 前问自己——"我要不要保留'对不上的'那部分？"
- 保留左表的 → left
- 保留右表的 → right
- 都不要 → inner
- 两张表是不是同一张？是 → 自连接（起别名）

## 十一、易错点总结

1. **字段撞车**：两表都有同名字段时，必须写 `表名.字段`
2. **笛卡尔积**：n 张表必须写 n-1 个关联条件，否则行数爆炸
3. **每个 join 带自己的 on**：不能等全部 join 完再写
4. **on 放关联条件，where 放筛选条件**：别混
5. **`where 子表字段 is null` 查"没配上"的部分**：写错字段或写 `dname is null` 容易出问题
6. **左表 = from 后面那张，右表 = join 后面那张**：别搞反
7. **自连接必须起别名**：同一张表起两个别名（emp / mgr），否则 MySQL 分不清两个视角
8. **自连接的关联条件**：`A表.指向字段 = B表.主键`（emp.mid = mgr.eid），方向别写反
9. **自连接用 inner 会丢掉"没配对"的行**（如老板 mid=NULL）→ 想全保留用 left join

## 十三、学习路线

1. **内连接**：交集 A∩B → 先学会"拿关联字段配对"
2. **左连接**：左表全留 → 只改一个单词
3. **右连接**：右表全留 → 记住 `A left join B` = `B right join A`，工作中基本只用 left
4. **查"没配上"的**：`where 子表关联字段 is null` → 面试高频
5. **自连接**：同一张表起两个别名，`A表.指向字段 = B表.主键` → 层级关系必备
6. **三表以上**：每个 join 带自己的 on，条件数 = 表数 - 1

> **心法：所有连接都是"拿关联字段配对"，区别只在"配不上的部分要不要留、留哪边的"，以及"配对的双方是不是同一张表"。**
